# Command interpretations

The engine is pure. The service owns account resolution, authorization, self-registration gating (`registrationOpen`), and desk views. Staff can add entrants while self-registration is closed. `allowLateEntry` gates `AddPlayers` after any round is paired; re-entry of an existing entrant uses the explicit re-entry commands.

- `ReEnroll` preserves existing matches and adds a bye loss for every missing round, including the current round. It does not displace another player or create a live pairing.
- `UndropPlayer` only handles the current round. `bye_loss` and `bye_win` add the corresponding one-player match. `next_round` only reactivates; it adds no match or historical backfill. Consequently, an unseated active player appears in integrity and blocks results and advancement until staff create a match or bye. This follows the explicit unpaired-player guard.
- `swap_with_dropped` requires `swapWith` to be another dropped player seated in an unscored current match. The returning player replaces that seat; the other player remains dropped and unseated. Pending reports are cleared. Fixed-table constraints are revalidated.
- `take_bye` uses the first current bye win held by an active player, removes that automatic bye and its points, and creates an unscored two-player match at an available table, respecting fixed seats. A bye loss is not eligible.
- `SplitMatch` removes only an unscored current match. `CreateMatch` and `AddByeMatch` require active, unpaired entrants. Existing tables stay fixed when adding a match. Byes have no table. A scored bye must be cleared before splitting or ordinary pairing edits.
- Entering a non-null result, reporting a result, advancing, cutting, and completing require every active player to have a current-round seat. Clearing a result remains possible during manual repair.
- `PairNextRound` requires at least two active players, including when starting single elimination or advancing playoffs. Zero active players return `NO_PLAYERS`; one returns `NOT_ENOUGH_PLAYERS`.
- `RepairRound` deletes the current round's results, pending reports, timer and extensions and re-pairs with a new command seed. Automatic byes and late-entry loss backfills are retained or regenerated. Current playoff eliminations are recalculated while earlier rounds and bracket seeding are preserved. The desk must confirm the number of reported results being deleted first. Send `{ type: "RepairRound", round: currentRoundNumber }` to reject an earlier selection or a round that has since advanced (`CURRENT_ROUND_ONLY`); omitting `round` targets the latest round.
- Swiss cuts require all results, affect only active players, and retain dropped players and match history. Top cuts use published standings keys; exact ties crossing the line use the command seed or a complete `tieOrder`. Undo restores only the last cut's still-cut players. Pairing locks undo through `roundPairedAfter`. Cancelling back to a cut's boundary or earlier restores its still-cut players and clears that flag, allowing `UndoSwissCut` again; older cuts and dropped players are preserved. Cut players cannot use `DropPlayer` to bypass the cut through re-enrollment.
- To cut and immediately pair, the desk sends `{ type: "SwissCut", mode: "top", value: count, pairNext: true }` (with `tieOrder` when needed) or `{ type: "SwissCut", mode: "min_points", value: points, pairNext: true }`. The command is atomic: if pairing fails, neither the cut nor the next round is saved. Omit `pairNext` for a cut without pairing.
- `CompleteEvent` requires every match to be reported. Temporary member IDs block completion only when `settings.requireMemberId` is true and an active entrant has one (`TEMPORARY_MEMBER_IDS`: "Temporary IDs must be replaced before finalizing"). Dropped/cut temporary entrants do not block it; optional-ID events may finalize with temporary IDs.
- Member IDs normalize at entry/update. Invalid syntax becomes null; a required missing ID is refused. Check digits and duplicate member IDs are advisory through integrity. Both temporary number ranges skip checksum warnings, while duplicate temporary IDs still warn. Accounts must be unique among entrants and separately among staff; a staff account may also play.
